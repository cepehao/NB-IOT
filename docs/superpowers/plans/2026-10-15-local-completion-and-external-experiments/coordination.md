# Как выполнять план несколькими агентами

Это инструкция к [единому плану](../2026-10-15-local-completion-and-external-experiments.md), а не новый маршрут. Владелец 19.10 прямо разрешил продолжить исполнение до проверяемого завершения доступного объёма ТЗ; старый запрет «только планирование» больше не действует. Принятые результаты сохраняются; текущая точка — T1 portable/preflight. P0/S0 и старые сообщения ниже описывают первоначальный запуск, не команду повторить baseline/ранние задачи. Продолжать по текущим locks, review и remaining-work-20261018.md, без повторного согласования обычных шагов.

**Порядок следующего исполнения:** S0 → U5-R1/D4-R1 по разным write sets → R4-close → D4-F/E/A/I → T1/T2 → T3; U3-refresh по независимым файлам. Обычные проверки в фоне, без activation окон. Терминальный report/cleanup своего worker и точная identity подтверждают завершение очереди; недоступное свёрнутое GUI не является blocker. Новые физические fixtures ≤2 UE, остальные пределы 300 с/файл и 900 с/набор сохраняются. Исторический R4.12 не читать/Apply/resume без отдельного решения владельца.

## Роли и ограничения

1. **Координатор:** читает весь план, раздаёт задачи, управляет блокировками файлов, запускает проверки, принимает результат. Только он изменяет общий статус и выполняет Git-операции.
2. **Исполнитель A:** одна выданная задача runtime/UI. Не меняет соседние модули без передачи владения.
3. **Исполнитель B:** одна выданная задача data/model/delivery. Одновременно с A работает только по непересекающимся файлам.
4. **Независимый ревьюер:** читает задачу, исходники, полный diff и отчёты; не редактирует код и не принимает собственную работу. Проверяет соответствие заданию, затем корректность и сопровождаемость.

Достаточно четырёх агентов, включая координатора. Для координатора/ревьюера нужна модель с хорошим рассуждением; исполнителям можно дать более простую. Не выбирать и не менять тариф/модель автоматически. Дополнительные вложенные агенты не нужны. Параллельность здесь разрешена владельцем для непересекающихся задач; MATLAB остаётся один.

**Глобальная блокировка проверки:** перед каждым MATLAB запуском оба исполнителя подтверждают паузу правок вычислительных исходников. Координатор сохраняет source manifest, выполняет один запрос через bounded runner, сохраняет итоговый manifest и сравнивает их. Во время проверки разрешены только документация/чтение. Изменился исходник — результат не относится к единому снимку; выяснить причину, затем повторить только затронутую проверку. Не запускать MATLAB напрямую, из агента или параллельного терминала.

## Цикл одного задания

1. Координатор проверяет ACCEPTED у зависимостей, фиксирует before snapshot и выдаёт эксклюзивные файлы. Другие исполнители эти файлы только читают. Если ожидается интерфейс другой задачи, работа ждёт принятия интерфейса.
2. Исполнитель читает указанные функции и тесты; пишет короткий failing test на обнаруженный дефект, затем минимальную реализацию. Не переносит чужие изменения и не реорганизует весь модуль.
3. Исполнитель отдаёт `TEST_REQUESTED`: список файлов, существенный diff, точную команду, ожидаемые результаты, ограничения. Сам MATLAB не запускает. Синтаксические/read-only проверки допускаются.
4. Координатор останавливает правки, запускает выбранные тесты через `verification/local/runBoundedChecks.ps1` (≤300 с файл/случай, ≤900 с запрос), проверяет exit status и MATLAB summary. Timeout/incomplete — провал проверки, не успех. Не повторять неизменённый timeout.
5. Ревьюер получает after snapshot и свидетельства. Сначала `SPEC PASS/FAIL`, затем `QUALITY PASS/FAIL`. Проверяет исходники, а не только отчёт исполнителя. Возвращает конкретный дефект: ID, важность, файл/строка, условие возникновения, что нарушено и проверка исправления.
6. Исполнитель устраняет замечания только в своей области. Координатор проверяет затронутые сценарии; ревьюер перечитывает исправление. После двух безуспешных циклов координатор разбирает причину и дробит задачу/уточняет контракт; не продолжать бесконечный цикл и не принимать дефект из-за лимита попыток.
7. ACCEPTED означает одновременно: реализация есть; относящиеся проверки прошли на этом снимке; reviewer принял; координатор сверил документы и ограничения. Только тогда снять блокировки и разрешить зависимую задачу.

Состояния: TODO → IN_PROGRESS → TEST_REQUESTED → TEST_PASS → ACCEPTED. При замечаниях REVIEW_CHANGES; при внешней зависимости BLOCKED с точным недостающим входом. Если ответ нужен лишь научному запуску/окончательной U3, программная часть задачи может быть ACCEPTED с отдельным externalGate=awaiting-professor; запрещённую операцию не выполнять. «Код написан» не равно «готово». Не закрывать P1/P2, влияющие на обязательное поведение, фразой «исправим позже».

Для diff учитывать новые файлы и исходный dirty baseline; сравнение только с HEAD смешает старую работу с новой. `git diff --no-index` возвращает 1 при наличии различий — это не ошибка чтения. Git stage/commit выполняет только координатор, по явным файлам/кускам после приёмки; `git add .`, reset/clean, push и публикация не входят в план. Если старые изменения нельзя отделить, сохранить проверяемые снимки и объяснить это, а не потерять чужую работу ради красивого коммита.

## Точные сообщения агентам

### Исполнителю

> Выполни только задачу {ID} из {packetPath}. Прочитай AGENTS.md и раздел задачи. Зависимости {IDs} приняты; тебе эксклюзивно принадлежат {files}. Before snapshot: {path}. Сохрани научные параметры, API вне задачи, named RNG и локальные ограничения. MATLAB не запускай; запроси у координатора точную bounded-команду. Не меняй чужие файлы и не делай Git-операций. Если контракт противоречит коду, сообщи конкретный файл/строку и останови зависимую часть, не придумывай обход. Отчёт: сделано / изменённые файлы / запрос проверки / риски / следующий шаг. Не ставь ACCEPTED сам.

### Ревьюеру

> Проверь только {ID} и интеграцию с уже принятыми зависимостями. Прочитай задание {packetPath}, before/after snapshots {paths}, diff включая новые файлы, source manifests и логи {paths}. Ничего не меняй и не запускай повторно без конкретной причины. Сначала SPEC PASS/FAIL (каждый критерий задачи), затем QUALITY PASS/FAIL (ошибки, регрессия, ресурсы, тесты). Не принимай development fixture за научное доказательство. Для замечаний укажи важность, файл/строку, воспроизведение и ожидаемый результат. Проверь, что тест вызывает рабочий путь, а не повторяет реализацию. Укажи непроверенное явно.

### Координатору при продолжении после перерыва

> Продолжи единый план по ledger, не начинай аудит сначала. Проверь активные процессы и locks, перечитай незавершённые карточки и последнее решение reviewer. Восстанови владельцев файлов. Продолжай первую готовую по зависимостям задачу. Старый вариант 2 не запускать. Если сохранённое состояние противоречиво, исправь описание по фактам, не переписывай научные файлы.

## Контроль времени и отчёт владельцу

Каждая задача получает оценку из пакета и запись фактического времени работы/ожидания/проверки. При превышении верхней оценки на 50% координатор сообщает причину, оставшийся конкретный блокер и пересмотр срока; не ждёт окончания суток. Это контроль хода, а не основание ослаблять требования.

После каждой принятой задачи — одно короткое сообщение: результат, что проверено, следующая задача. При длинной операции — видимая фаза, последнее содержательное продвижение и оставшийся лимит. Не оставлять активную сессию часами в ожидании без решения.

Стоп-условия: неожиданные >10 UE/большой физический запуск; требование ослабить научный критерий; неизвестная процессная identity; попытка принять fixture для науки; несовместимый checkpoint; необходимость менять фиксированный PHY-профиль без решения U3. Сохранить свидетельства, остановить зависимую операцию, продолжить независимые задачи. Новые внешние расходы/сообщения/публикации не подразумеваются.
