# O2: календарь нисходящего канала

## Изменения

Изменения внесены только в `work/optimization-candidate`. Рабочая копия проекта и `work/optimization-baseline` сохранены без изменений.

- `src/+nbiot/+scheduler/Scheduler.m`: построены один раз индекс разрешённых DL-тиков и префиксная сумма; реконструкция календаря сохраняет прежний порядок выдачи ресурсов.
- `src/+nbiot/+scheduler/ResourceCalendar.m`: аналогичный индекс ускоряет поиск первых четырёх monitoring DL-тиков.
- Добавлены `tests/TestDlCalendarIndex.m` и `tests/TestMonitoringTickIndex.m` с проверками границ горизонта, задержек и формы результата.

## Проверки и результаты

- Сначала новые тесты падали на отсутствующих индексах; после реализации целевые тесты прошли **11/11**, полная серия — **54/54** (`o2-final-suite*`).
- Эталонное и оптимизированное одно-UЕ выполнение после изменений сравнены независимым O1 harness: `o2-final-comparison.json` сообщает **26/26 проверок пройдено**, включая MAT-результат, статусы, KPI, таблицы и SHA-256 шести CSV-файлов.
- Микробенчмарк `Scheduler.reconstructDownlink`: ускорение **1,69× / 2,04× / 1,27×** для позиций 5/1000/4000. `monitoringTicks`: **46,21× / 29,36× / 10,16×**. Сырые `timeit`-замеры находятся в `o2-benchmark-baseline.mat` и `o2-benchmark-candidate.mat`.
- Полные прогоны кандидата: 100 UE — **1460,48 с**, 1000 UE — **4763,3 с**. Прогон 1000 UE быстрее архивного сопоставимого результата 5106,70 с на **343,40 с (6,72%)**. KPI для обоих размеров точно совпали с сохранёнными сводками. Детали и машинная сверка — `o2-large-summary.json`; сводка прогонов — `o2-load/manifest.csv`.

## Границы вывода

На одно-UЕ end-to-end прогоне ускорения нет: 24,54 с у кандидата против 22,98 с у baseline. Поэтому подтверждённый результат — выигрыш для сценария 1000 UE и микробенчмарков календаря, а не универсальное ускорение всех нагрузок. Для 100 UE нет сопоставимого старого непрофилируемого wall-clock замера; KPI совпадает с архивной сводкой.
